# План 2026-10: довести laravel-admin до витрины

Цель — три вещи, которые человек со стороны может взять и использовать:

1. **Внедрение в готовый проект** — `composer require` + одна команда, без чтения
   кода demo/printable.
2. **Каркас нового приложения** со встроенной админкой —
   `composer create-project dskripchenko/laravel-admin-skeleton`.
3. **Публичный стенд** на самой админке: витрина (формы, гриды, навигация,
   дашборды) и полная документация внутри неё же — каждый пример живой, рядом
   его код. Ориентир — orchid.software, но у Orchid только лендинг и доки, а
   живое демо мертво (`demo.orchid.software` не отвечает).

Аудит от 2026-10-01 — основание плана: ядро технически здорово (923 PHP-теста,
418 фронтовых, pint/phpstan/typecheck чистые), но установка по докам даёт белую
страницу, примеры getting-started падают, а заметная часть бэкенд-API не
рисуется SPA. Витрина «каждого поля и раскладки» эти дыры покажет первой —
поэтому трек A идёт до трека D.

Хостинг стенда: отдельный VPS (машину выбирает автор), домен — поддомен
`dev-cloud.space` (рабочее имя `admin.dev-cloud.space`).

---

## Трек 0. Гигиена (быстро, до остального)

- Удалить пустой `forge/laravel-admin/` и `forge/laravel-admin.zip` (ядро
  живёт в `forge/core`).
- `package.json` ядра: убрать зависимость пакета от самого себя
  (`"@dskripchenko/laravel-admin": "^1.8.0"`).
- README ядра: требования (сейчас «PHP ^8.5 / Laravel ^12», в composer —
  `^8.2`, L11–13), список sister-packs (search/quill/tinymce в архиве), состав
  starter (Settings/Translations/Blocks там нет).
- `docs/internal/roadmap.md`: убрать архивные пакеты, дописать 1.31–1.32.
- GitHub Releases ядра обрываются на v1.19.3 при тегах до v1.32.0 — догнать
  (из CHANGELOG), health/jobs v1.4.0 — тоже без Release.
- Sister-packs (все живые): `version()` из `InstalledVersions` вместо
  `'0.1.0'`; метки через `__()` + словари en/ru; тег публикации в README
  (`admin-*-config`); нижняя граница ядра `^1.30`; CI по расписанию
  (раз в неделю) — ловить дрейф ядра.
- CHANGELOG ядра на английском (канон «доки пакетов — по-английски»).

## Трек A. Ядро: паритет бэкенда и SPA

Принцип: всё, что объявлено в PHP и в доках, рисуется в SPA по-настоящему.

**A1. Тест паритета реестров** (первым, он задаёт объём работ): каждый
`fieldType()` / layout `type()` / `chartType` / тип действия из PHP имеет
компонент на фронте. Сейчас красный — и остаётся красным, пока A2–A5 не
закроют список.

**A2. Раскладки**: Modal и Drawer (в том числе вызов из commandBar и из
действия), Wizard со степпером (шаги, валидация шага, `persistKey`),
Accordion (сворачивание, `multi`), View, Infolist и AuditTrail на экранах.

**A3. Действия**: ModalAction — форма в модалке и `payload` на сервер;
AsyncAction с прогрессом (delayed-process); Link и DropDown; подтверждение —
модалка `@dskripchenko/ui` вместо `window.confirm`; **баг**: confirm у действий
ресурса не показывается (`ResourceIndexPage.vue:156` ждёт строку, бэкенд шлёт
`{message,title}`).

**A4. Поля** — настоящие компоненты вместо упрощений: markdown (редактор +
превью), code (подсветка), color, radio, slider, rating, date_range, time,
tree_select, cascader, morph_switcher. Часть — в `@dskripchenko/ui`
(канон: UI-примитивы чиним/добавляем там).

**A5. Графики**: radar, несколько серий (line/bar/area), легенда.

**A6. Listeners** — главная фича Orchid, которой у нас нет: перерисовка части
формы при изменении поля (серверный метод экрана/ресурса получает состояние,
возвращает обновлённые поля/значения). `visibleWhen` остаётся для простых
случаев.

**A7. Уведомления**: toast из `alerts` ответа, единый стиль success/error.

**A8. OpenAPI** (открытые пункты roadmap): разметка `action`/`save`/
`tokenCreate`, поля `create`/`update` (зависит от laravel-api). На публичном
стенде `/api/doc` открыт — пробелы будут видны.

## Трек B. Внедрение в готовый проект

**B1. Фронт без сборки по умолчанию.** Сейчас хост обязан собрать свой
`admin.js` и прописать `assets.vite_*`, иначе shell молча отдаёт белую
страницу. Предлагается:
- npm/composer-поставка **готовой сборки приложения** (не только библиотеки):
  `admin:install` публикует её в `public/vendor/admin`, shell подключает её
  по умолчанию — админка работает сразу после `composer require` + install;
- режим «своя сборка» для расширений (свои поля/виджеты): `admin:install
  --custom-build` генерирует `resources/js/admin.js`, дописывает entry в
  `vite.config.*`, выставляет `assets.vite_*`;
- shell при пустых assets показывает понятную ошибку, а не пустой div;
- `admin:link` — привести в соответствие или удалить.

**B2. `admin:install` как мастер**: публикация конфига и миграций, выбор
стратегии пользователей (`dedicated` — свой guard и `admin_users`, или
`shared` — хостовый User + `HasAdminAccess`), migrate, создание супер-админа,
опционально `--examples` (демо-экраны) и `--starter` (Users/Roles/Audit).
Ссылки — на опубликованные доки, а не на исключённый из дистрибутива
`docs/ARCHITECTURE.md`.

**B3. Документация внедрения** (en/ru): установка в существующий проект шаг
за шагом; dedicated vs shared; префикс и домен; несколько панелей;
совместная работа с laravel-api хоста (`api_module`); обновление версий;
чек-лист «что проверить после установки».

**B4. Исправить getting-started и concepts** (en/ru): `admin:user`,
методы TableColumn (`sort()`, `search()`, `asBadge()`), URL просмотра. Примеры
из доков проверять в CI (doc-tests: сниппеты собираются в тестовый ресурс и
проходят запрос к API).

**B5. Проверка на живом проекте**: внедрение в printable (уже на ядре) не
показательно — нужен «чистый» прогон: свежий `laravel new` + существующие
модели → по докам до работающей админки, Playwright-смоук.

## Трек C. Каркас нового приложения (`laravel-admin-skeleton`)

Новый репозиторий, публикация на Packagist как `project`:
- Laravel 13, PHP ^8.3, Vite настроен, готовая сборка админки;
- starter-ресурсы (Users, Roles, Audit), настройки, профиль, 2FA;
- супер-админ из `.env` при первом запуске, `composer setup`;
- один пример ресурса + экрана + дашборда (удаляемые одной командой);
- Docker compose (php-fpm/octane + nginx + postgres/sqlite) и вариант без
  Docker (`php artisan serve` + sqlite);
- CI: тесты + Playwright-смоук (вход, CRUD, экран);
- README en/ru, ссылка на стенд.

## Трек D. Публичный стенд: витрина + документация на самой админке

Переделка `laravel-admin-demo` (сейчас ~40% готовности, lock на ядре 1.12.6,
33 отладочных скрипта в корне, стенда нет).

**D1. Витрина** (ветка меню Showcase):
- *Dashboards*: метрики, графики всех типов, виджеты, редактирование сетки.
- *Forms*: каждое поле (в т.ч. связи, файлы, даты, repeater/builder,
  translatable), группировка и раскладки, валидация, listeners, wizard.
- *Grids*: сортировка, фильтры всех типов, поиск, пагинация, массовые
  действия, inline-edit, итоги, сохранённые представления, экспорт/импорт,
  soft-delete, дерево, embed-table, reorder.
- *Layouts*: rows/columns/tabs/accordion/block/modal/drawer/infolist.
- *Navigation variants*: многоуровневое меню, бейджи, группы, права на
  пункты, глобальный поиск ⌘K.
- *Notifications*, *Files/Media*, *Users/Roles/Permissions* (вход под
  разными ролями), *i18n* (ru/en), *брендинг и темы*, *несколько панелей*.
- Один реалистичный домен целиком (магазин: товары/заказы/клиенты +
  блог), а не только синтетика.

**D2. Документация как экраны.** Ветка меню Docs повторяет дерево Orchid,
дополненное нашими отличиями: Get Started (установка в проект, каркас,
конфигурация, брендинг, обновление) → Tutorials → Core Concepts → Layouts →
Fields → Grids → Actions → Advanced → Packages.
- Страница доки — экран: markdown из `docs/{en,ru}` ядра + блоки «Пример»:
  живой компонент и вкладки PHP / JSON-ответ. Код и рендер берутся **из
  одного класса** (атрибут вида `#[DocExample]`) — не расходятся.
- Таблица API (fluent-методы поля/колонки/раскладки) — генерируется
  рефлексией.
- Перекрёстные ссылки: в витрине «Как это сделано» → док; в доке «Открыть в
  витрине».
- Языки en/ru; de/zh-заглушки из навигации убрать до перевода.
- «Предложить правку» → файл в GitHub.

**D3. Доступ и устойчивость стенда.** Вход без регистрации (кнопки «войти
как admin/editor/viewer» на форме входа), сброс данных по расписанию
(`migrate:fresh --seed` раз в час), throttle на мутации, квота загрузок,
запрет опасного (смена пароля, 2FA, impersonation — read-only).

**D4. Лендинг** на корне домена: hero с кнопкой «Открыть демо», ключевые
возможности со скриншотами из смоука, установка в 3 команды, ссылки на
GitHub/Packagist.

**D5. Защита от устаревания**: Playwright обходит все страницы Showcase и
Docs и проверяет, что каждый пример рендерится без ошибок; тот же прогон
снимает скриншоты для лендинга и README.

**D6. Деплой**: отдельный VPS, домен `admin.dev-cloud.space` (рабочее),
CI-деплой по тегу/ветке, отдельный стек по образцу стендов printable.
